# Super Admin Credential Rotation & Security Runbook

## Executive Summary

The AxonX Medtech Hospital Management System (HMS) includes an active security guard, [`KnownDefaultCredentialGuard`](file:///e:/Projects/HOSPITAL/backend/src/main/java/com/hms/security/KnownDefaultCredentialGuard.java), that executes on startup (`@PostConstruct`) in all non-development profiles (`production`, `prod`, `staging`, `qa`, etc.).

If ANY active user with role `SUPER_ADMIN` holds a known public default credential (such as the development password `pass123` or published documentation hashes), **startup is refused immediately and the application halts**.

> [!IMPORTANT]
> **Zero-Bypass Policy:**
> Under NO circumstances should `KnownDefaultCredentialGuard` be disabled, bypassed, or modified to permit default credentials in production environments. Default super-admin accounts present an immediate, critical platform-takeover vulnerability.

---

## 1. Information Security & Leak Prevention

- **Log & Exception Redaction:** Startup exceptions and logs generated by `KnownDefaultCredentialGuard` and `DataInitializer` **never output password hashes or plain-text passwords**. They disclose only the affected account's e-mail address and account count.
- **Digest Comparison:** Published BCrypt hashes from repository history are stored in source code as SHA-256 digests (`KnownDefaultCredentials.PUBLISHED_HASH_DIGESTS`), ensuring published hashes themselves are not echoed.

---

## 3. Remediation Procedures

### Option 1: Deactivate Legacy Development Accounts (Recommended for Staging/Restores)

If an environment was seeded from a development snapshot containing `admin123@gmail.com`, and that account is not in active administrative use, deactivate it directly in the database:

```sql
UPDATE users
SET is_active = 0
WHERE email = 'admin123@gmail.com' AND role = 'SUPER_ADMIN';
```

- **Why this works:** Deactivated accounts (`is_active = 0`) are excluded from `userRepository.findActiveSuperAdminCredentials()`. The authentication filter rejects tokens and logins for inactive users, so inactive accounts cannot be exploited.

3. **Verify Hash Pattern:**

   ```sql
   SELECT id, email, is_active,
          password REGEXP '^[$]2[aby][$][0-9]{2}[$][./A-Za-z0-9]{53}$' AS is_valid_bcrypt
   FROM users
   WHERE email = 'admin123@gmail.com';
   ```

---

### Option 3: Initial Deployment Bootstrap via Environment Variables

For greenfield deployments with an empty database, [`DataInitializer`](file:///e:/Projects/HOSPITAL/backend/src/main/java/com/hms/component/DataInitializer.java) creates the first Super Admin automatically if and only if valid bootstrap credentials are provided via environment variables:

```bash
export INITIAL_SUPER_ADMIN_EMAIL="admin@yourhospital.com"
export INITIAL_SUPER_ADMIN_PASSWORD="YourStrongPassword123!"
```

#### Password Complexity Requirements:

The application enforces strict validation on initial credentials:

- **Length:** At least 12 characters.
- **Character Classes:** Must contain at least one uppercase letter, one lowercase letter, one digit, and one symbol/special character.
- **Forbidden Values:** Must not equal `pass123` or use email `admin123@gmail.com`.
- **Completeness:** If only one of the two variables is set, startup fails immediately.

> [!NOTE]
> Once a Super Admin exists in the database (`existsByRole('SUPER_ADMIN') == true`), `DataInitializer` skips bootstrap execution. Subsequent startups ignore these environment variables.

---

## 4. Verification Check

After applying either Option 1 or Option 2, restart the service or run the preflight verification query:

```sql
SELECT email, is_active, role
FROM users
WHERE role = 'SUPER_ADMIN';
```

When the application boots:

- The log should display:
  `Known-default credential check passed: no active super admin uses a public default.`
- Readiness probe (`/actuator/health/readiness`) transitions to `UP`.
